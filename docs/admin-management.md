# 管理画面・DB・移行

## 公開・非公開・予約公開

登録済み店舗の編集フォームには赤い「店舗を削除」ボタンがあります。確認ダイアログの店舗名を確認して「削除する」を押すと、一覧・公開マップ・重複判定から除外されます。キャンセル時は変更しません。内部では削除日時と操作履歴を保持する論理削除を使い、再インポートで復活しないようにしています。同名店舗をまとめて削除することはありません。別の更新があった場合は削除を拒否します。

管理画面の「掲載状態」で「公開」「非公開」「予約公開」を選び、店舗情報を保存します。予約公開は日本時間で日時を指定します。指定時刻以降のページアクセスから公開対象となり、開いたままのページは再読み込みで反映されます。閉店・一時休業・移転の店舗は公開対象になりません。公開または非公開に切り替えると予約日時を解除します。

マイグレーション `0003_publication_schedule.sql` は既存店舗をすべて非公開にし、変更履歴を残します。以降の初期インポートも非公開で登録します。移行の再実行では管理画面で変更した公開設定を保持します。

「公式サイト」は公開用の専用URLです。情報元URLは内部記録として保持しますが、公開ページには渡さず、管理画面のURL入力も公式サイトだけを表示します。既存の情報元URLは公式サイトとは限らないため自動転用しません。公式サイトを確認して入力してください。

`npm run test:unit` で入力検証、`npm run test:integration` で専用のローカルD1を使った予約公開・解除・再インポートを検証できます。

## 起動と操作

Node.js 24以上で `npm ci` → `npm run db:setup` → `npm run dev` を実行します。初期ログインは `/admin/login`、ユーザー名・パスワードともに `admin` です。環境変数は `.env.example` を参考に `.env.local` に設定できます。

管理画面では登録店舗の検索・編集、手入力での新規登録、取得候補からの新規登録ができます。店舗名、住所、エリア、種別、ビル、階、緯度・経度、位置の根拠、情報元URL、SNS URL、確認日、営業状態、掲載状態を変更できます。緯度・経度は両方入力するか、両方空欄にします。

候補からの新規登録は下書きで開始します。同名店舗、または同じ情報元URLの店舗がある場合は重複の可能性を表示し、既存店舗の編集へ切り替えられます。候補の選択だけでは店舗を保存しません。公開・下書き・非公開と、営業中・未確認・閉店等は独立した項目です。公開設定でも閉店・一時休業・移転はマップから除外します。公開マップは再読み込み時に最新のDBを取得します。

## 保存構造

ローカル・本番ともにCloudflare D1の `DB` bindingを使用します。ローカルの保存先は `.wrangler/state` です。スキーマは `db/migrations/` のSQL、接続は `src/infrastructure/database/d1.ts`、店舗操作は `d1-cafe-store.ts` が担当します。移行元のSQLiteは読み取り専用で扱い、アプリの実行時には使用しません。構築・デプロイは [Cloudflare Workers・D1の構築手順](./cloudflare-d1.md) を参照してください。

| テーブル | 用途 |
| --- | --- |
| cafes | 掲載情報、営業・掲載状態、位置、URL、確認日、更新version |
| buildings / floors | エリア・ビル名・街区で識別したビルと階 |
| administrators / sessions | パスワードのscryptハッシュ、トークンのSHA-256ハッシュと有効期限 |
| login_attempts | 失敗回数と15分間の再試行制限 |
| cafe_history | 更新者、変更前後、変更日時 |
| collection_runs / collected_candidates | 過去の取得実行と候補の原データ |
| import_records | 旧台帳の原データ、移行記録 |
| search_candidates | 管理画面で検索した候補 |
| d1_migrations | WranglerによるSQLマイグレーションの適用履歴 |
| schema_migrations | 移行元SQLiteのスキーマ履歴 |

店舗・ビル・階・履歴をD1の `batch()` で原子的に保存します。編集時のversionが古い場合は409を返し、同時更新もDBのversionトリガーで拒否して上書きを防ぎます。DB制約とdomainの入力検証で種別・状態・座標・URLを検証します。セッションは24時間有効で、HttpOnly・SameSite=StrictのCookieを使用し、ログアウト時に失効させます。管理ページとAPIは認証必須です。変更リクエストのOriginをHostと照合します。

本番はWorkersからD1へ接続するため、アプリ用の永続ディスクは不要です。バックアップは `npm run db:export:remote` で出力します。本番の `SESSION_COOKIE_SECURE=true` は `wrangler.jsonc` に設定済みです。

## 既存データの移行

`npm run db:setup` は次を実行します。

1. ローカルD1へSQLマイグレーションを適用します。
2. 既存SQLiteがあれば、店舗の編集内容、管理者、更新履歴、収集履歴、旧台帳を読み取り専用で取り込みます。ログインセッションは移行しません。
3. SQLiteがなければJSONから初期データと管理者を作成します。現在の掲載・営業状態と未取得座標を保持します。
4. 初回移行後はD1の店舗情報を保持し、取得実行・候補の新規分だけを追加します。
5. `reports/d1-import.sql` と `reports/d1-import-summary.json` を出力します。失敗がある場合は終了コード1です。

実装時の初回移行では店舗63件（狸小路10件・すすきの53件）、全取得履歴197候補、旧台帳8件を保存しました。移行元ファイルも残しています。営業未確認の店舗を営業中に変更する処理はありません。

再実行時はD1の店舗情報・掲載状態・編集versionを保持します。初回移行完了後にバッチで見つかった新規候補は公開店舗へ自動追加せず、候補テーブルへ保存します。管理画面から確認・登録してください。本番D1の取り込みは `npm run db:setup:remote`、生成レポートの件数は移行元の件数です。

## 候補検索

検索語は2〜100文字です。登録店舗、過去の収集候補（直近5,000レコード）、検索履歴（直近500候補）、補完候補を検索します。全角・半角、英字大小、ひらがな・カタカナ、空白・記号の差を吸収し、スペース区切りの複数語で店舗名・住所を照合します。保存済みのSNS URLも検索対象で、XのURL・アカウント名に対応します。店舗名の一致を優先し、業態の接頭辞や住所表記による重複をまとめます。別フロアは分けます。

「外部サイトも検索」を選ぶとポケパラ・かふぇこんの一覧を各3ページ、店舗詳細を各5件まで確認します。結果は関連度順に最大30件です。補完候補は `src/infrastructure/admin/data/supplemental-candidates.json` に参照先と確認メモを保持します。検索エンジンで確認できても既存の収集対象に含まれない店舗を補うためのもので、公開店舗への登録は管理者が確認してから行います。

robots.txt、Crawl-delay、アクセス間隔は取得バッチと共通です。媒体間は並行、同じ媒体内は順次取得します。外部取得全体に30秒の中断シグナルを設定し、リクエストと待機にも適用します。失敗時は警告と取得できた候補を表示します。検索中はローダーモーダルを表示します。掲載ページの存在だけでは営業中と確定しません。

「Googleでも店舗を探す」は検索語を引き継いでGoogleを別タブで開くリンクです。GoogleやX全体を自動検索するAPIは接続していません。保存済み候補に含まれないXアカウントは、URLだけから自動取得できません。

Windowsの信頼済み証明書が必要な環境では、起動前に `$env:NODE_OPTIONS="--use-system-ca"` を設定します。TLS検証を無効にはしません。SNSはリンク情報を扱い、投稿・雑誌本文の取得、全店舗の網羅、自動的な閉店判定、ユーザー登録・パスワード再発行は今回の初回実装に含みません。
