# 店舗情報の取得・更新方法

## 独立した取得バッチ

`batch/collect-cafes.mjs` を `npm run cafes:collect` で手動実行します。DBや定期ジョブは使用しません。ポケパラのすすきのコンカフェ一覧、かふぇこんの札幌・すすきの一覧をページ送りまで巡回し、店舗詳細の構造化データと店舗情報欄から事実項目を抽出します。既存台帳の公式URLも取得します。画像・紹介文・キャストプロフィール本文は保存しません。

取得結果は `data/collections/<実行ID>/{tanukikoji,susukino}/001.json` 以降に100件ずつ保存します。実行ごとに別ディレクトリを作るため、件数減少時に以前の分割ファイルが混ざりません。全結果を書き終えた後、`latest.json` の参照を更新します。0件のエリアも空配列ファイルを作ります。対象エリアを住所から判断できない店舗はmanifestのexcludedに記録します。

取得日時はfetchedAt、媒体の更新日時はupdatedAtに保存します。掲載ページがあるだけでは営業中とせず、営業未確認はunknown、店舗自身の見出しに明示的な閉店表示があるものはclosedとします。閉店表示のないことは営業中の証明になりません。取得候補はpublishable=falseとし、地図の公開台帳に自動追加しません。名前・住所が一致する候補をまとめ、異なる住所の同名店は移転や別店舗の可能性として保持します。

SNSは店舗ページのリンクだけを収集し、ログイン制限を回避しません。投稿の取得には別のAPIアダプタが必要です。雑誌の紙面・電子書籍は未取得です。robots.txtとCrawl-delayを尊重し、最低1秒の間隔と20秒のタイムアウトを使用します。HTTPエラーや取得形式の変更はmanifestに記録し、部分取得を全量取得として表示しません。

地図用の確認済み台帳も `src/infrastructure/cafes/data/{tanukikoji,susukino}/001.json` 以降へ分割しました。100件以下・エリア一致・ID重複などをリポジトリ読み込み時に検証します。

## アプリへの反映

アプリは現在、`CollectionCafeRepository` で最新の取得スナップショットをリクエスト時に読み込みます。営業未確認の候補もラベル付きで表示します。閉店・一時休業・移転の候補は除外します。座標がない場合は一覧に表示し、ピンは推測して配置しません。今回の収集バッチ自体が出力する状態はunknownと見出しで検出したclosedで、一時休業・移転の自動検出は未実装です。休業・移転の状態が追加された際にもアプリは除外します。

`publishable=false` は営業確認済み台帳へ昇格できないことを示します。アプリでの候補表示は、営業中として確認済みの表示ではありません。部分取得の実行は全量表示せずエラーにします。SNS投稿・雑誌本文の取得や営業状態の確認は引き続き未対応です。

## 原因と今回の変更

以前は動作確認用の2店舗をTypeScriptに直接記載していたため、検索や情報取得を行っていませんでした。今回、公式サイト・運営会社の店舗一覧から確認した8店舗をJSON台帳に移し、読み込み時にID重複、種別、エリア、座標、確認日、確認元を検証します。狸小路4店舗・すすきの4店舗で、地域の全店舗を網羅したデータではありません。

## 技術比較

| 方法 | 用途と長所 | 制約 | このプロジェクトでの扱い |
| --- | --- | --- | --- |
| Google Places Text Search | 店名・キーワード・地域から候補を発見。店舗詳細と営業状態もAPIで取得できる | 課金・APIキー・保存制限・帰属表示が必要。地図上のPlacesデータ表示はGoogle Mapが必要。コンカフェの独自分類には目視確認が必要 | 現在のLeaflet/OSMへそのまま取り込む方式は採用しない |
| OpenStreetMap / Overpass | 公開されたPOIを範囲・タグで取得できる | 店舗登録・業態タグの網羅性は保証されない。ODbLへの対応が必要 | 候補発見の補助として検討。OSMだけで全店舗取得とはしない |
| 公式サイトのJSON-LD | LocalBusinessのname・address・geoをHTMLから構造化して抽出できる | 未導入・誤記・複数店舗の混在がある。営業中とは限らず、SNSだけの店舗も拾えない | 確認済みURLの更新調査に採用。公開を自動確定しない |
| HTML抽出 / ブラウザ自動化 | JSON-LDがない店舗・JS描画ページにも対応できる | DOM変更、アクセス制限、利用条件、robots.txtへの対応が必要 | 静的HTMLを先に確認し、必要なサイトのみ個別アダプタを検討 |
| 事業者提供データ / 手動台帳 | 独自分類、階数、閉店・移転を確認できる。小規模で導入しやすい | 更新作業が必要。自動で網羅性・鮮度は上がらない | 当面の公開元。将来は管理画面と店舗からの訂正受付を追加 |

参考：[Places Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search)、[Placesの保存・表示ポリシー](https://developers.google.com/maps/documentation/places/web-service/policies)、[Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API)、[Schema.org LocalBusiness](https://schema.org/LocalBusiness)。

住所から座標を求める処理と、店舗を発見する処理は別です。公開Nominatimは最大1リクエスト/秒、識別可能なUser-Agent、結果キャッシュなどの制限があり、地域の全POIを取得する用途は禁止されています。本アプリには組み込んでいません。[公式利用ポリシー](https://operations.osmfoundation.org/policies/nominatim/)

## 採用する流れ

1. 店舗・運営会社の公式一覧、店舗の公式SNS、専門ディレクトリなどから候補を探す。第三者一覧だけで確定しない。
2. 公式情報で所在地・業態・閉店や移転の告知を確認する。名称と住所を正規化して既存店舗と照合する。同じ建物でも店名・フロアが違えば別店舗。
3. 公式のJSON-LDやアクセス情報で座標を確認する。埋め込み地図の「中心座標」を店舗位置として流用しない。建物位置しか確認できない場合はその精度を記録する。
4. 確認したレコードだけを `src/infrastructure/cafes/data/{tanukikoji,susukino}/001.json` 以降へ100件以下ずつ登録する。ID、area、category、locationGroup、coordinateSource、sourceUrl、verifiedOnを保持する。
5. 台帳検証とテスト後に公開する。取得失敗は閉店と扱わず、以前の確認済みデータを保持して再調査する。閉店・移転は公式の根拠を記録して反映する。

狸小路は公式に狸小路店と案内される店舗と南2〜3条の商店街周辺、すすきのは南4条以南の歓楽街周辺を目安とし、各店舗にエリアを明示します。行政境界の判定ではありません。メイドカフェはmaidを優先し、その他はconceptとします。同じ建物の店舗をlocationGroupでまとめ、地図では数付きピンから個別店舗を選べます。

## 更新調査コマンド

```bash
npm run cafes:audit
```

実行前に取得対象サイトの利用条件を確認してください。robots.txtで禁止されたページは取得せず、robots.txtの取得エラー時もそのサイトを取得しません（404は制限指定なしとして扱います）。台帳の公式URLだけを順番に取得し、JSON-LDの店舗候補と現在の台帳を `reports/cafe-source-audit.json` に出力します。15秒でタイムアウトし、アクセス間隔は1秒、HTTPエラー時の自動再試行はありません。JSON-LDがなければ手動調査が必要です。抽出した他店舗や位置の不一致を自動採用せず、確認日も更新しません。実際の店舗発見や閉店確認まで自動化したクローラーではありません。

Windowsで証明書エラーが起きる場合は、信頼済み証明書を使って実行できます。

```powershell
$env:NODE_OPTIONS = "--use-system-ca"
npm.cmd run cafes:audit
```

次の段階では、公開台帳と候補データを別ファイルで保持し、差分・重複チェック → 営業確認 → 公開の流れを実装します。更新履歴、閉店状態、失敗時の再調査、店舗からの訂正受付を追加することで運用上の網羅性と鮮度を改善します。定期ジョブは設定していません。
